# FRIDAY Agent UX 重塑记录

记录日期：2026-05-10

## 产品定位

FRIDAY 不是 Obsidian 里的编码 Agent，也不是把 Claude Code / Codex / Manus 逐像素搬进侧边栏。

Obsidian 是 FRIDAY 的一个前端入口。FRIDAY 的目标是在 Obsidian 中陪伴用户开展泛文档类工作：整理、改写、归档、生成、检查、复盘、连接上下文。它应该亲和、克制、不粘人，让普通白领用户觉得安全、从容、可控。

本阶段先不学习或重做这些能力：

- 上下文压缩；
- Subagent；
- 后台任务体系；
- 工作区隔离。

这些差距明显，但不进入当前交互重塑范围。

## 对标产品的可取点

### Claude Code

Claude Code 的强项在于 agent harness 的纪律性：工具边界清楚、文件变更有审阅、执行过程可以回溯、危险动作有权限控制。

FRIDAY 应该学习的是这种边界感，而不是把 `tool`、`diff`、`checkpoint`、`debug`、`replay` 等工程概念直接暴露给普通用户。

### Codex 桌面端

Codex 的强项在于让用户知道 agent 正在做什么：当前动作、等待用户确认、失败恢复、继续执行都比较明确。

FRIDAY 应该学习的是“当前状态优先”和“动作靠近状态”，不是学习 coding IDE 式的工具轨迹密度。

### Manus

Manus 的强项在于过程叙事：先给出非承诺式响应状态，再说明理解和计划，过程中用简短语言告诉用户刚做了什么、接下来做什么。

FRIDAY 应该学习的是这种陪伴式、可扫读的进度表达，同时避免让每一步都显得需要用户关注。

## 对标产品背后的交互哲学

FRIDAY 应该全面参照 Claude Code、Codex、Manus 的 agent harness 哲学，但不能照搬它们的界面对象。

### Claude Code 的启发

学习重点：先判断任务形态，再决定协作方式。

Claude Code 的 `plan mode`、权限模式、变更审阅都体现了一个核心原则：agent 不应该把所有用户请求都当成同一种流程。简单问题直接答，复杂任务先理解和规划，涉及修改时进入可确认状态。

FRIDAY 要吸收这种任务分流能力，但不要把 `plan mode`、`accept edits`、`permission mode` 这类开发者概念暴露给普通白领用户。

### Codex 的启发

学习重点：行动边界清晰，当前状态可见，但过程不抢主内容。

Codex 的哲学是：低风险动作自动推进，高风险动作明确中断；运行时让用户知道当前正在做什么；失败、重连、审批都要明确显示，不能假装顺利。

FRIDAY 要吸收这种安全和状态哲学，但将 `sandbox`、`approval policy`、`tool call`、`model request` 翻译成普通用户能理解的语言。

### Manus 的启发

学习重点：用户交付目标，agent 持续推进。

Manus 强调“把任务交给 agent 后，它会继续工作”。FRIDAY 也应支持用户收起插件、切换对话、回到文档编辑时继续执行任务。

但 FRIDAY 运行在 Obsidian 中，面对的是用户知识库和文档资产，因此不能用过强的全自动行动感压过用户的控制感。涉及文件写入、删除、外部动作时，必须让用户清楚知道哪些已经发生，哪些仍待确认。

### FRIDAY 的翻译原则

用户只需要知道四件事：

- FRIDAY 是否已经开始；
- FRIDAY 正在做什么；
- 是否需要我决定；
- 最终交付了什么。

其它内部阶段默认隐藏。

## 当前需要重塑的核心问题

### P0：用户消息后的首响和任务路由必须模型主导

当前重点问题：用户发送消息后，FRIDAY 应该先显示什么、什么时候开始正式理解、简单回答还是拆任务，这些判断不能主要由前端或 runtime 的正则规则决定。

正确流程应该是：

```text
用户发送
-> 本地临时状态：FRIDAY 正在响应……
-> 模型请求成功发出：FRIDAY 正在理解你的请求……
-> 模型返回 intake：
   - direct_answer
   - clarify
   - light_task
   - task_with_process
-> UI 根据 intake 决定是否展示过程面板、计划、审批、动效
-> runtime 只负责连接状态、安全边界、失败兜底
```

规则：

- 本地首响不是正式 assistant message，不应持久留在对话里；
- 本地首响不能说“已收到”“我理解你要...”，因为模型可能还没有连上；
- 请求发出后可以显示 `FRIDAY 正在理解你的请求……`；
- 网络失败时显示：`暂时没能连接到模型。你的消息已保留，但 FRIDAY 还没有开始处理。`
- 模型返回 intake 后，再由模型说明“我理解你想要……我会……”；
- 简单回答、澄清问题、轻量任务、完整任务过程由模型在 intake 中判断；
- runtime 可以做安全兜底和格式兜底，但不应再用正则语义判断压过模型意图；
- 如果模型没有返回合法 intake，runtime 才使用保守 fallback。

四种推荐路由：

- `direct_answer`：直接回答，不保留过程面板；
- `clarify`：只问一个必要澄清问题；
- `light_task`：展示轻量运行状态，不制造完整计划感；
- `task_with_process`：运行中默认展开过程面板，完成后折叠。

### P0：文件变更审批的心智模型必须重做

当前困惑：创建新文件、修改文件时，FRIDAY 有时会表达成“已经创建”或“已经修改”，但实际上需要用户审批后才生效。

这会造成错误心智：用户感觉 FRIDAY 已经动了自己的文件，然后才让自己事后追认。

正确心智应该是：

- 用户请求本身授权 FRIDAY 准备方案；
- FRIDAY 可以先生成待应用的文件变更草案；
- 在用户确认前，不得说“已创建 / 已修改 / 已删除”；
- 只有用户点击应用并实际写入 Vault 后，才能说“已创建 / 已修改 / 已删除”；
- 如果 FRIDAY 想做用户没有明确要求的文件动作，必须先做意图确认。

推荐表达：

- 运行中：`我会先准备一版待确认的修改，不会直接写入文件。`
- 等待确认：`已准备好 1 个待应用的文件修改，确认后才会写入 Obsidian。`
- 应用后：`已创建 / 已修改 ...`
- 拒绝后：`已取消，未写入任何文件。`

实现约束：

- `pending_review` 状态下禁止展示完成态文案；
- final answer 如果仍有 pending mutation，必须说“已准备好变更，等待你确认”；
- `本次改动` 只能展示已经应用的文件，不展示待审批草案；
- mutation review 的按钮应该是 `应用修改` / `不应用`，而不是工程权限语言；
- 普通文件创建、写入、编辑、删除走单一 mutation review，不再叠加 tool approval。

### P0：审批模型要从工程权限改成用户决策

普通用户不应该面对 `Allow once / Allow session / Allow always` 这种权限系统。

FRIDAY 用户层只需要理解：

- 这件事要不要做；
- 是否要把这批变更应用到文件；
- 是否允许一个明显高风险的外部动作。

推荐拆分：

- 文件变更：`应用修改` / `不应用`；
- 高风险工具：`允许执行` / `拒绝`；
- 非用户明确要求的范围扩展：先问“是否继续”。

当前项目里的审批触发应按这个方向收敛：

- 只读类动作不打扰用户；
- 标准模式下，普通文件变更进入一次文件变更审阅；
- `exec`、外部访问、编译/生成类非文件副作用才进入高风险授权；
- 禁止把 `write`、`edit`、`delete` 这种工具名直接给普通用户看。

### P0：审批态应接管底部聊天输入框本体

当 FRIDAY 等待用户确认时，审批不应该只是对话流里的一张卡片，也不应该藏在过程面板深处。

正确位置应该是用户准备继续输入的地方：底部 composer。

规则：

- 审批态直接占用聊天输入框的正文区域；
- 原本输入文本的位置替换为审批面板；
- composer chrome 保留，包括模型选择、权限模式、`+Skill`、`@` 等上下文控制；
- 用户在该状态下的主要动作是处理审批，而不是继续输入一段新 prompt；
- 如果允许排队输入，也应是次级能力，不能和审批主动作抢焦点；
- 文件变更审批显示 `应用修改` / `不应用`；
- 高风险非文件动作显示 `允许执行` / `拒绝`；
- 审批处理完成后，composer 恢复正常输入状态。

这样做的心智模型是：FRIDAY 暂停在一个需要用户决策的关口，用户下一步不是“聊天”，而是“决定是否继续”。

### P0：执行过程面板运行时默认展开，完成后默认折叠

FRIDAY 在执行过程中展示“正在做什么”是必要的，它能让用户觉得安全。

但这种展示不应该要求用户持续盯着看。

规则：

- 任务型工作运行时默认展开过程面板；
- 最终答案输出后，过程面板默认折叠；
- 如果处于等待审批、等待用户输入、失败恢复状态，保留显眼但克制的 action-required 状态；
- 用户把插件收起、切换会话或转去别处时，FRIDAY 应继续工作；
- 过程信息应可扫读，不要变成日志终端。

### P1：运行状态应使用安静的 Obsidian-native 微动效

Codex 和 Manus 都会通过 UI 动效让用户感到 agent 仍在推进。FRIDAY 也可以做，但方向应该更克制。

推荐动效：

- `FRIDAY 正在响应……`：轻微呼吸点或三点节奏；
- `FRIDAY 正在理解你的请求……`：过程面板自然展开，当前状态点缓慢高亮；
- 执行动作中：只突出当前动作，工具轨迹默认折叠；
- 重连或网络不稳定：温和但明确的状态提示；
- 等待审批：短暂吸引注意，然后保持静止；
- 完成后：过程面板折叠，最终答案成为主内容。

实现约束：

- 优先使用 scoped CSS 和状态 class；
- 不引入复杂动画库；
- 使用 Obsidian 主题变量，不硬编码强烈色彩；
- 动画只使用 `opacity`、`transform`、少量 `box-shadow`；
- 必须支持 `prefers-reduced-motion`；
- 动效必须由真实状态驱动，不能用本地假进度伪装执行。

### P1：隐藏内部工程阶段

不要默认展示太多 agent 内部阶段。

普通用户不需要看到：

- `tool`;
- `checkpoint`;
- `model request`;
- `raw reasoning`;
- `trace`;
- `runtime event`;
- `replay/debug`。

需要展示的是：

- 收到任务；
- 理解了什么；
- 准备怎么做；
- 刚刚完成了什么；
- 接下来做什么；
- 是否需要用户处理；
- 是否遇到连接问题并正在恢复。

模型连接问题必须用用户语言告知，例如：

- `模型连接不稳定，FRIDAY 正在重试。`
- `请求多次未成功，请稍后再试或检查模型配置。`

不要把它表现成产品静默卡死。

### P1：工具轨迹默认折叠，只给语义摘要

工具轨迹对安全感有价值，但不能成为默认主内容。

规则：

- 默认展示语义摘要，例如“读取了 2 个相关文件”“准备了 1 个待确认修改”；
- 具体工具名、参数、原始结果默认折叠；
- 展开后也要使用用户能理解的标签，不要直接暴露 raw JSON；
- 工具失败如果 FRIDAY 还能继续，应表达为“遇到问题，正在换一种方式继续”，不是立刻失败。

### P1：不要给普通用户 replay / debug 入口

当前产品不应默认存在高级用户。

replay、debug、checkpoint 等能力可以作为内部诊断能力保留，但不应出现在普通用户默认界面里。完成后的过程回顾只作为次级折叠入口存在，用于复盘关键过程，不用于调试。

### P1：回答、过程、产物三者必须分层

最终答案是主内容。

过程区解释 FRIDAY 正在做什么，但不能压过答案。

产物区展示本轮已经应用的文件成果，应该在最终答案之后。

规则：

- 简单直接回答：只显示轻量 `FRIDAY 思考中`，完成后不保留过程面板；
- 任务型工作：运行中显示过程，完成后折叠为次级回顾；
- 已应用文件：放到 `本次改动`；
- 待审批文件：停留在审批状态，不进入 `本次改动`；
- 最终答案不能被 completed lifecycle card 顶下去。

### P2：插件前端形态不是完全错误，但重心要调整

当前插件前端最大问题不是“有过程面板”这件事错了，而是过程面板和审批 UI 容易带出 coding agent / 内部控制台气质。

FRIDAY 应该是 Obsidian-native 的文档工作伴侣，而不是一个嵌在 Obsidian 里的 IDE terminal。

方向：

- 保持安静、密集、可扫读；
- 少用大卡片、重阴影、营销式装饰；
- 不把工程对象当作用户对象；
- 审批和状态靠近输入区或当前任务状态；
- 文案以“我准备 / 我正在 / 需要你确认 / 已完成”为主，不以工具名为主。

### P2：FRIDAY 的语气要亲和但不黏人

FRIDAY 不应该每一步都请用户关注，也不应该显得过度解释自己。

推荐语气：

- 简短；
- 主动；
- 清楚；
- 不甩锅；
- 不暴露内部实现；
- 不假装已经完成未完成的事。

避免：

- `正在调用 write 工具`;
- `checkpoint saved`;
- `model_request failed`;
- `我已经修改了文件，请审批`;
- `Allow always`;
- `debug replay`。

## 下一步建议

1. 先改用户发送后的本地首响、模型连接态和 intake 路由，因为这是 agent 感知入口。
2. 再改文件变更审批的状态和文案，因为这是信任问题。
3. 再改审批按钮和权限模型，把普通文件变更从工具权限里剥离出来。
4. 接着调整过程面板默认展开/完成折叠规则。
5. 最后做过程叙事、工具轨迹折叠和 Obsidian-native 微动效，把 FRIDAY 从工程日志感改成文档工作陪伴感。

## 验收标准

- 本地首响不作为正式 assistant message 持久保存。
- 网络失败时不说“已收到”或“正在理解”，而是明确说明模型尚未开始处理。
- 模型返回 intake 后，才展示正式理解和行动方向。
- 简单回答、澄清、轻量任务、完整任务过程主要由模型判断。
- runtime 不再用正则规则主导语义任务分流，只做安全、连接和兜底。
- 审批前绝不出现“已创建 / 已修改 / 已删除”。
- 用户能明确知道“确认前不会写入 Obsidian”。
- 普通文件变更只出现一次应用确认。
- 高风险非文件动作才显示授权确认。
- 审批态占用底部聊天输入框本体，并保留 composer chrome。
- 运行中的任务型工作默认展示过程。
- 完成后的过程默认折叠，最终答案保持主位。
- 工具、checkpoint、model request、debug、replay 不进入普通用户默认界面。
- 网络或模型连接问题必须用用户语言显示恢复状态。
- 运行状态有克制的微动效，并尊重 `prefers-reduced-motion`。
- FRIDAY 可以持续工作，但不会让用户感觉每一步都需要盯着。
