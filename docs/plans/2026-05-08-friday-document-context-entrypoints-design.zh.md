# FRIDAY 文档内入口与上下文任务设计备忘

> **状态：** 产品设计备忘。本文用于记录 2026-05-08 关于 FRIDAY 是否必须打开工作台才能开始工作的讨论，避免后续实现时丢失决策背景。

**目标：** 让 FRIDAY 可以从 Obsidian 文档现场自然进入工作流，而不是要求用户先打开 FRIDAY 工作台再开始对话。

**核心决策：** 从文档中发起的 FRIDAY 能力分成三类：

- **轻量内容修改任务**：后台静默运行，直接作用于当前选区，类似 Notion AI。
- **FRIDAY 白板暂存任务**：把原文、文件或修改意图先贴到白板/便签墙，暂不执行。
- **复杂理解与协作任务**：拉起 FRIDAY 工作台，在新对话中展示来源上下文并允许继续追问。

---

## 1. 背景

当前 FRIDAY 的主要入口是工作台。用户如果想让 FRIDAY 处理正在看的文档，通常需要先打开 FRIDAY，再把当前笔记、选中文本或文件路径带入对话。这对复杂任务是合理的，因为用户需要看到历史、过程、审批和后续追问；但对润色、缩短、翻译这类低风险文本变换来说，这个路径太重。

我们希望 FRIDAY 更像 Obsidian 内的原生工作伙伴：用户仍然以文档为中心浏览、写作和整理，FRIDAY 在需要时从右键菜单、选区操作或角落入口出现。工作台不消失，但它不应该是唯一入口。

新的入口模型必须同时满足两点：

- 不打断轻量写作流。
- 对复杂任务保留可追问、可解释、可追踪的对话空间。

## 1.1 整体功能评估

截至目前，这组讨论已经形成一套从文档现场进入 FRIDAY 的产品能力，而不是单点功能。

| 新产品功能 | 解决的问题 | 需要建设的新能力 | 预计实现方案 |
|---|---|---|---|
| 文档选区右键 FRIDAY 菜单 | 在阅读/写作现场直接调用 FRIDAY | `ObsidianContextMenuRegistrar`、选区文本/range 捕获、菜单动作分流 | 用 Obsidian `editor-menu` / `file-menu` / `files-menu` 注册入口 |
| 轻量 inline 修改，类似 Notion AI | 润色、缩短、翻译不应打开对话 | `InlineAgentTaskService`、受限 prompt、只替换当前选区、失败不污染文档 | 后台调用模型，成功后 `Editor.replaceSelection()`，不创建会话 |
| 从文档发起新对话 | 解释术语、讨论选区、把多个文档加入新对话 | `ConversationIngressService`、结构化上下文包、上下文卡片、自动/不自动发送规则 | 把当前 `DailyBoardView` 里的对话发起能力抽成服务，打开工作台并创建新会话 |
| 拖拽文件/文件夹到对话框等同 `@` | 用户不想用 `@` 搜索器，想直接拖入上下文 | drop payload 解析、Vault 路径识别、项目边界校验、public `insertMentionToken()` | 给 composer 增加 `dragover/drop`，解析成现有 `MentionToken`，复用现有 mention resolver |
| FRIDAY 白板 / 便签墙 | 用户阅读时先收集修改点，最后统一交给 FRIDAY | `Board`、`BoardNote`、`SourceAnchor`、`BoardBatch` 实体；状态管理；来源追踪 | 白板作为新实体，但优先复用 Obsidian Canvas 承载 UI |
| 一键打开 FRIDAY 白板 | 原生 Canvas 启动链路太重 | 白板创建/打开服务、工作区分屏策略、默认路径管理 | 命令或按钮 `打开 FRIDAY 白板`，自动创建 `.canvas` 并打开 |
| 添加到白板 | 把原文、文件、文件夹、修改建议先贴到白板 | 右键小输入框、最近选区快照、Canvas node 追加、sidecar 元数据 | 右键添加写入 Canvas text node；拖拽则尽量使用 Obsidian Canvas 原生能力 |
| 白板批量发送到新对话 | 用户整理完一批便签后让 FRIDAY 统一检查和执行 | `BoardBatch`、Canvas + sidecar 解析、冲突/重复/过期检查 | 从白板选择便签，生成新对话上下文，先检查一致性，再进入修改计划 |
| 浮动 FRIDAY 入口 | 用户没打开工作台时也能召唤 FRIDAY | 全局 launcher、位置设置、隐藏/拖拽、mini chat 或跳转工作台 | 第二阶段做，可选开启，不作为主入口 |

优先级判断：

1. 先做选区右键菜单、轻量 inline 修改、文档发起新对话。
2. 同批可以做拖拽文件/文件夹到对话框生成 `@`，因为它不引入新实体，复用现有 mention 链路。
3. 白板确定复用 Obsidian Canvas 基础设施，但具体存储位置、使用方法和 FRIDAY 使用白板的逻辑需要继续确认。
4. 浮动 FRIDAY 入口放到第二阶段，避免入口过多导致产品心智发散。

## 2. 任务分层

### 2.1 轻量内容修改任务

轻量任务的特征：

- 输入主要是当前选区。
- 输出可以直接替换原文。
- 用户通常不需要完整对话历史。
- 任务失败时给出轻提示即可。
- 权限边界应限制在当前选区或当前文件。

典型入口：

- `润色选中内容`
- `缩短选中内容`
- `扩写选中内容`
- `改成更正式`
- `翻译选中内容`
- `提取为待办`

交互原则：

1. 用户选中一段文字。
2. 右键打开菜单，选择 FRIDAY 的轻量动作。
3. FRIDAY 在后台运行受限任务。
4. 成功后直接替换选区。
5. 显示轻提示：`已替换，可 Ctrl+Z 撤销`。

这类任务不应该默认新建对话，也不应该强制打开 FRIDAY 工作台。它的产品心智是 inline edit，不是 chat。

建议命名为 `Inline Agent Task`。

### 2.2 复杂理解与协作任务

复杂任务的特征：

- 用户需要解释、讨论、追问或持续协作。
- 输入可能来自选中文本、当前文档、多个文件、文件夹或文档树多选。
- FRIDAY 的回答需要有上下文卡片、来源记录和后续对话空间。
- 任务可能触发工具、计划、审批或长时间后台执行。

典型入口：

- `解释选中内容`
- `这个词是什么意思`
- `发送到新对话`
- `添加到新对话中`
- `基于当前笔记开始对话`
- `基于选中的多个文档开始对话`
- `把这个文件夹作为上下文`

交互原则：

1. 用户在编辑器、阅读视图、文件树或文档列表中选择内容。
2. 右键选择 FRIDAY 的复杂任务入口。
3. FRIDAY 创建一个新的对话上下文包。
4. 打开 FRIDAY 工作台。
5. 新对话顶部显示来源上下文卡片。
6. 根据动作类型决定是否自动发送第一条问题。

例如：

- `解释选中内容` 可以自动发送：`请解释这段内容。`
- `这个词是什么意思` 可以自动发送：`这个词在当前文档语境中是什么意思？`
- `添加到新对话中` 更适合只创建上下文，不自动发送，让用户继续输入。

建议命名为 `Conversation Ingress Task`。

### 2.3 FRIDAY 白板暂存任务

白板暂存任务介于 inline edit 和完整对话之间。它不是人的待办清单，而是 FRIDAY 的待处理修改材料池：用户阅读文档时不断收集原文、问题、修改意见和参考文件，FRIDAY 先不执行，等用户整理完再统一交给新对话检查和处理。

建议入口心智：

```text
Inline Agent Task        立即处理当前选区
FRIDAY 白板 / 便签墙      暂存多个修改意图，稍后批处理
Conversation Ingress     直接进入新对话讨论
```

命名建议：

- 产品入口叫 `白板`。
- 面向修改场景的白板类型叫 `修改便签墙`。
- UI 文案中避免直接叫 `待办`，因为待办容易被理解为人的任务管理。

典型场景：

1. 用户阅读一篇文档。
2. 发现多个需要修改的点，但不想每发现一个就让 FRIDAY 执行一次。
3. 用户把每个点贴到白板上，像贴便签一样收集。
4. 每张便签记录原文、来源和用户标注。
5. 用户整理完后选择一批便签，发送到新对话。
6. FRIDAY 先检查逻辑冲突、重复建议、范围重叠和原文是否已变化。
7. 没问题后生成修改计划，再进入 diff / 审批 / 应用。

重要原则：

- 收集阶段绝不执行。
- 便签是用户授权前的意图材料，不是 FRIDAY 自动会做的任务。
- 执行必须由明确动作触发，例如 `发送到新对话` 或 `检查并执行`。

## 3. 右键菜单设计

编辑器选中文本后的菜单建议结构：

```text
FRIDAY
  润色选中内容
  缩短选中内容
  扩写选中内容
  翻译选中内容
  添加到白板...
  ---
  解释选中内容...
  发送到新对话...
```

文件树单选文件后的菜单建议结构：

```text
FRIDAY
  基于这篇笔记开始对话...
  添加到新对话...
  添加到白板...
```

文件树多选后的菜单建议结构：

```text
FRIDAY
  添加到新对话...
  基于这些文档开始分析...
```

菜单分组原则：

- 直接改变文档内容的动作放在上半区。
- 会打开工作台的动作放在下半区，并用省略号暗示会进入下一步界面。
- 高风险写入动作必须可撤销，或在替换前提供预览。
- `添加到白板...` 不执行修改，只收集材料和意图。

## 4. 上下文包模型

复杂任务不要只是把文本粘进输入框，而应该创建结构化上下文包。

建议数据结构：

```ts
type FridayDocumentIngressContext = {
  source:
    | "editor-selection"
    | "editor-active-file"
    | "file-tree-selection"
    | "folder-selection";
  intent:
    | "explain"
    | "define-term"
    | "discuss"
    | "new-chat-context"
    | "analyze-documents";
  selectedText?: string;
  files: Array<{
    path: string;
    title?: string;
  }>;
  ranges?: Array<{
    path: string;
    from: { line: number; ch: number };
    to: { line: number; ch: number };
  }>;
  createdAt: string;
};
```

对话中应该显示：

- 来源类型：选中文本、当前笔记、多选文档、文件夹。
- 文件路径或标题。
- 选区摘要。
- 是否已自动发送第一条问题。

## 5. 工程拆分建议

当前 FRIDAY 的对话发送逻辑主要集中在 `DailyBoardView`。为了支持文档内入口，需要把“发起任务”的能力拆出视图层。

建议新增或演进以下模块：

### 5.1 `ObsidianContextMenuRegistrar`

职责：

- 注册 `editor-menu`。
- 注册 `file-menu`。
- 注册 `files-menu`。
- 根据是否存在选区、文件数量、文件类型生成 FRIDAY 菜单项。
- 不直接执行业务逻辑，只调用下游服务。

### 5.2 `InlineAgentTaskService`

职责：

- 接收选区文本、文件路径、选区范围和轻量动作类型。
- 构造受限 prompt。
- 调用模型或 agent runtime 的轻量路径。
- 返回替换文本。
- 由调用方使用 Obsidian `Editor.replaceSelection()` 替换选区。

约束：

- 默认不创建对话历史。
- 默认不使用跨文件工具。
- 默认不写当前选区以外的内容。
- 失败时不污染文档。

### 5.3 `ConversationIngressService`

职责：

- 接收选区、文件、文件夹或多选文件上下文。
- 创建新的会话。
- 将上下文包注入会话。
- 根据入口类型决定是否自动发送第一条用户消息。
- 打开 FRIDAY 工作台并定位到新会话。

约束：

- 不直接替换文档内容。
- 保留来源上下文，便于用户理解 FRIDAY 看到的材料。
- 与完整工作台共用同一套对话持久化和任务进程展示。

## 6. FRIDAY 白板 / 便签墙

### 6.1 实体模型

白板需要作为新的 FRIDAY 实体引入，不能混同为会话草稿或人的待办。

建议实体层：

```text
Board / 白板
  -> BoardNote / 便签
    -> SourceAnchor / 来源锚点
    -> Instruction / 用户意图
    -> Status / 状态
  -> BoardBatch / 一次提交给 FRIDAY 的便签集合
```

建议数据结构：

```ts
type FridayBoard = {
  id: string;
  title: string;
  scope: "global" | "project";
  projectId?: string;
  status: "collecting" | "frozen" | "sent_to_chat" | "archived";
  activeBatchId?: string;
  createdAt: string;
  updatedAt: string;
};

type FridayBoardNote = {
  id: string;
  boardId: string;
  kind: "change" | "question" | "idea" | "reference";
  text: string;
  instruction?: string;
  sources: FridayBoardSource[];
  targetProjectId?: string;
  status: "captured" | "ready" | "sent_to_chat" | "applied" | "stale" | "dismissed";
};

type FridayBoardSource = {
  type: "selection" | "file" | "folder" | "manual";
  path?: string;
  projectId?: string;
  selectedText?: string;
  range?: {
    from: { line: number; ch: number };
    to: { line: number; ch: number };
  };
  textHash?: string;
};
```

`BoardBatch` 用来表示用户从白板中选择一批便签后提交给 FRIDAY 的一次处理任务。FRIDAY 不应该默认处理整块白板，而应该处理用户明确选择的一批便签。

白板生命周期本身应进入第一版。即使第一版不做自动执行修改，也需要清楚区分白板当前是否还在收集、是否已经提交给 FRIDAY、是否应该清空或归档。

### 6.2 项目边界

白板的信息来源是否受项目管理，需要区分收集和执行。

建议规则：

- 白板可以跨项目收集。
- 白板便签可以没有项目。
- 来源如果能匹配某个 FRIDAY 项目，就记录 `projectId`。
- 来源不在任何项目内，也可以记录，但标记为 `out_of_project`。
- 当用户要 `发送给 FRIDAY 执行修改` 时，必须选择一个目标项目。
- FRIDAY 只能读取和修改目标项目边界内的来源。
- 跨项目便签可以一起发送到对话里讨论，但不能一次性跨项目写入，除非未来明确支持 multi-project execution。

产品分层：

```text
收集阶段：自由、低摩擦、跨来源
整理阶段：白板里分组、筛选、合并、删除
执行阶段：绑定项目、检查冲突、生成计划、审批修改
```

### 6.3 两种添加到白板的方式

#### 方式一：右键添加，带意图采集

适合用户已经知道要怎么改。

```text
选中原文 -> 右键 FRIDAY -> 添加到白板 -> 小输入框写修改建议 -> 生成便签
```

生成的便签天然更接近可执行修改点：

```text
原文：……
建议：这里要改成更口语 / 逻辑不清 / 加一个例子
来源：某文件第 x 行
状态：已标注
```

#### 方式二：拖拽添加，先贴上去再整理

适合用户阅读时快速摘取，不想马上停下来写建议。

```text
选中原文 -> 拖到已打开的 FRIDAY 白板 -> 生成便签 -> 在白板上编辑/标注
```

这个模式更像真实白板：先把材料贴上去，再移动、分组、补备注。拖进来的便签可以先是 `未标注` 状态，用户之后再补“希望 FRIDAY 怎么处理”。

技术上，drop target 可以先读 `text/plain`。来源路径和选区 range 需要插件维护最近选区快照；如果 drop 的文本能匹配最近选区，就附带来源；匹配不上，就当成普通手动便签。

### 6.4 UI 方向

白板页不应该做成普通列表，而应该尽量利用真实白板和便签的心智：

- 便签可以自由摆放、拖动、分组。
- 不同类型便签用不同颜色区分：修改、问题、摘录、想法。
- 便签内容保留“原文”和“我的标注”两个区域。
- 来源用小徽标显示：`来自当前文档`、`来自项目外`、`原文已变化`。
- 支持选择一批便签后发送到新对话。

但 UI 仍应克制。FRIDAY 运行在 Obsidian 内，不应把白板做成重型设计工具。第一版优先打通“贴便签 -> 标注 -> 选一批 -> 交给 FRIDAY”闭环。

### 6.5 第一版白板生命周期

第一版必须支持白板生命周期管理，但不做复杂的异常兜底。建议生命周期为：

```text
收集态 collecting
  用户可以自由添加、移动、删除、编辑便签。

冻结态 frozen
  用户点击“打包给 FRIDAY”后，当前白板或被选择的便签批次暂时不可继续编辑。

已发送 sent_to_chat
  FRIDAY 将这批便签整理成新对话的上下文，用户在对话里继续确认、讨论或要求执行。

完成后 archived / cleared
  FRIDAY 任务完成后，归档本批次记录，并清空当前白板中的已提交便签。
```

失败或取消时，不应清空白板，而应解除冻结，让用户继续整理。

第一版推荐采用“冻结后提交”的方式，而不是提交时立刻清空：

1. 用户在白板中自由整理内容。
2. 用户选择一批便签，点击 `打包给 FRIDAY`。
3. FRIDAY 冻结这批便签，并创建 `BoardBatch`。
4. FRIDAY 打开新对话，把便签内容和来源信息作为上下文放进去。
5. 对话任务完成后，FRIDAY 清空或归档这批已提交便签。
6. 如果任务失败、取消或用户关闭对话，则保留便签并解除冻结。

这样可以避免用户刚提交就丢失材料，同时保证同一批便签不会在 FRIDAY 处理过程中继续变化。

### 6.6 第一版暂不兜底的来源异常

以下三类异常需要记录为已知限制，但第一版不做自动恢复：

1. 用户已经把原文和意见添加到白板后，又修改了原文档内容，导致原文匹配不上。
2. 用户已经把原文和意见添加到白板后，又在白板里改写了引用原文，导致它不再等于源文档中的原文。
3. 用户添加材料后，原文件被移动或重命名，而用户没有更新路径，导致白板里的来源路径失效。

第一版不需要实现自动重定位、模糊匹配、路径搜索或冲突合并。FRIDAY 只需要让用户理解如何让它读懂修改点：

- 尽量在完成一批阅读和标注后再统一打包给 FRIDAY。
- 打包前不要大幅改动源文档中的对应原文。
- 白板上的“原文”应尽量保持为引用材料，具体修改想法写在用户意见节点里。
- 如果源文件移动或重命名，用户需要重新添加来源，或在白板中补充说明。

第一版提交给 FRIDAY 时，如果来源不可用或明显不一致，可以把该便签作为普通文字材料带入对话，但不承诺自动写回原文档。这个约束要在 UI 和文案里明确表达。

## 7. 复用 Obsidian Canvas

后续讨论中，我们重新评估了是否要自研白板。结论是：白板肯定要复用 Obsidian 原生 Canvas 等已有基础设施，不自研完整白板画布。

原因：

- Obsidian Canvas 已经支持把文字、文件和文件夹拖入画布。
- Canvas 已经有成熟的自由布局、文件卡片、文本卡片、分组和连线交互。
- `.canvas` 文件是 JSON Canvas 格式，FRIDAY 可以程序化创建和追加节点。
- 自研白板会重复实现大量已有交互，成本和维护风险都更高。

新的定位：

```text
Obsidian Canvas = 白板 UI 和基础交互
FRIDAY = 启动、收集、结构化、发送给对话、执行前检查
```

FRIDAY 应该重点解决两个痛点：启动和填入。至于白板最终放在哪里、用户如何在 FRIDAY 中选择和管理白板、FRIDAY 如何读取白板并决定哪些内容可执行，还需要继续确认。

### 7.1 启动问题

原生 Canvas 的能力很强，但用户启动一个空白白板通常需要：

1. 在文件树里新建 `.canvas`。
2. 手动打开。
3. 拖到合适工作区。
4. 自己决定分屏。

这对 FRIDAY 场景不够友好。

FRIDAY 应提供：

- `打开 FRIDAY 白板`。
- 如果没有白板，自动创建一个 `.canvas`。
- 自动在右侧或相邻分屏打开。
- 后续可以支持 `为当前项目打开白板`、`为当前文档打开白板`。

候选路径：

```text
F.R.I.D.A.Y/白板/收集箱.canvas
F.R.I.D.A.Y/白板/某项目修改建议.canvas
```

这只是候选方案，不是最终决策。存储位置需要继续权衡：

- 放在 `F.R.I.D.A.Y/白板/`：便于 FRIDAY 管理和发现，但可能让用户感觉内容被放进插件空间。
- 放在项目目录内：更符合项目边界和同步，但跨项目收集不方便。
- 放在用户指定位置：最符合 Obsidian 用户习惯，但需要额外配置和发现机制。

待确认问题：

- 是否默认创建一个全局收集箱白板。
- 是否为每个项目自动创建项目白板。
- 全局白板中的项目外来源如何进入执行阶段。
- 白板是否应该出现在 FRIDAY 工作台导航里，还是只作为 Obsidian Canvas 文件被打开。

### 7.2 填入问题

FRIDAY 应提供比原生 Canvas 更低摩擦的填入方式：

- 选中文本右键：`添加到 FRIDAY 白板...`
- 自动把选区追加为 Canvas text node。
- 如果用户写了修改建议，同时写入便签内容或 sidecar 元数据。
- 文件/文件夹可以作为 Canvas file node 进入白板。
- 白板已打开时，用户仍可使用 Obsidian 原生拖拽。

### 7.3 Canvas 与 FRIDAY 元数据

Canvas 可以承载视觉卡片，但 FRIDAY 需要的结构化信息不一定适合全部写进 Canvas 节点正文。

建议采用双层存储：

```text
白板.canvas              // 用户看到和操作的 Obsidian Canvas
白板.friday-board.json  // FRIDAY 的结构化元数据
```

sidecar 元数据记录：

- Canvas node id 与 FRIDAY 便签 id 的映射。
- 来源路径。
- 选区 range。
- 原文 hash。
- 修改建议。
- 状态。
- 目标项目。

这样既保留 Obsidian 原生 Canvas 的强交互，也让 FRIDAY 可以稳定判断哪些节点是可处理的修改便签。

待确认问题：

- sidecar 是否和 `.canvas` 同目录同名保存。
- sidecar 是否属于 Vault 内容，是否参与同步。
- 如果用户复制、移动或重命名 Canvas，sidecar 如何跟随。
- 如果用户只保留 Canvas、不保留 sidecar，FRIDAY 是否能从节点正文降级恢复部分信息。

### 7.4 FRIDAY 使用白板的逻辑

白板不是自动任务队列。FRIDAY 使用白板时应遵循：

1. 用户显式选择一个白板或一批便签。
2. FRIDAY 读取 Canvas 节点和 sidecar 元数据。
3. FRIDAY 区分普通素材、问题便签、修改便签和文件引用。
4. FRIDAY 做基础来源读取和项目边界判断，但第一版不做复杂自动恢复。
5. FRIDAY 把检查结果放入新对话，而不是直接执行。
6. 只有用户确认后，才进入修改计划、diff、审批和应用。

第一版的重点是把用户整理好的修改点输入给 FRIDAY。原文变化、白板引用被改、文件路径失效等问题先作为已知限制记录，不在第一版中为用户做完整兜底。

这部分逻辑仍待细化，尤其是：

- 用户如何从 Canvas 原生 UI 中选择“这批便签”。
- FRIDAY 如何识别用户手动创建的普通 Canvas 节点是否应该进入批处理。
- 白板中的文件节点是作为完整文件上下文、文件引用，还是只作为讨论材料。
- 多个白板是否能合并发送到同一个新对话。

## 8. 拖拽到对话框等同 `@`

拖拽文件或文件夹到 FRIDAY 对话框，也应该作为第一批可做的低成本改进。

产品规则：

```text
拖一个 Markdown 文件进输入框 -> 插入 @ 文件名
拖一个文件夹进输入框 -> 插入 @ 文件夹名/
拖多个文件进输入框 -> 插入多个 @ token
拖当前项目外文件 -> 提示不在当前项目边界内，不能作为执行上下文
```

它不引入新实体，只是给现有 `@` 引用增加拖拽入口。用户心智很清楚：拖到输入框等于添加为上下文。

技术路径：

- composer 增加 `dragover` / `drop` 处理。
- 优先解析 Obsidian 内部 drag data。
- 其次解析 `text/plain`、`text/uri-list` 或文件系统路径。
- 能映射回 Vault 路径时，判断是 `TFile` 还是 `TFolder`。
- 复用现有 mention scope 规则，转成 `MentionToken`。
- 插入 composer，显示成现有 `@` token。

实现时需要注意：Obsidian 内部拖拽在 `DataTransfer` 里具体放什么字段，需要在真实 Obsidian 环境中打日志确认。解析失败时应忽略，不要把无意义文本塞进输入框。

## 9. 与浮动 FRIDAY 入口的关系

浮动头像入口仍然有价值，但它不应该替代右键菜单。

建议定位：

- 右键菜单负责“基于当前内容做什么”。
- 浮动头像负责“随时召唤 FRIDAY”。
- 白板负责“先收集多个材料或修改意图，稍后批量处理”。
- 工作台负责“长对话、历史、审批、工具过程和后台任务状态”。

浮动头像可以作为第二阶段实现：

- 可关闭。
- 可拖拽。
- 可选择角落。
- 默认不遮挡正文。
- 点击打开 mini chat 或 FRIDAY 工作台。

## 10. 风险与护栏

### 10.1 静默替换风险

轻量任务虽然不进入对话，但仍然会修改用户文档。必须保证：

- 只替换当前选区。
- 替换后 Obsidian 原生撤销可用。
- 失败时不替换。
- 长文本替换前可以考虑预览。

### 10.2 任务分类错误

如果用户选择 `润色`，但选中文本包含复杂要求，FRIDAY 仍应按轻量任务处理，不应私自升级为复杂 agent 工作。入口动作决定默认交互形态，除非用户明确选择进入对话。

### 10.3 上下文过大

文件树多选可能包含大量文档。需要在进入对话前做预算控制：

- 显示已选择文件数量。
- 对超大上下文进行摘要或提示。
- 不要静默吞掉文件。

### 10.4 白板与 Canvas 风险

复用 Obsidian Canvas 时，需要避免 FRIDAY 过度接管用户的画布：

- 维护已有 Canvas 时要保留未知字段、已有节点 id、节点顺序和用户布局。
- FRIDAY 自动追加节点应尽量避免覆盖用户手动排版。
- sidecar 元数据丢失时，Canvas 仍应作为普通 Obsidian 白板可用。
- 如果 Canvas 节点被用户删除，sidecar 元数据应能清理或标记失效。
- 批量执行前最终需要重新读取文件，确认原文没有变化；但第一版只记录风险，不做复杂的自动重定位或恢复。

第一版已知限制：

- 如果源文档内容在添加到白板后被修改，FRIDAY 可能无法判断该便签对应哪段新原文。
- 如果用户在白板中改写了“原文”节点，FRIDAY 会把它当作用户整理后的材料，而不是可靠的源文档锚点。
- 如果源文件移动或重命名且 sidecar 路径未更新，FRIDAY 可能只能把便签作为普通文字材料带入对话。

用户使用建议：

- 一批修改点收集完后尽快打包给 FRIDAY。
- 需要 FRIDAY 精准写回时，不要把白板里的原文节点当作修改意见区使用。
- 文件移动或重命名后，重新从当前文件添加一次来源最可靠。

## 11. 第一版建议范围

第一版优先做：

- 编辑器选区右键菜单。
- `润色选中内容` 作为第一个 `Inline Agent Task`。
- `解释选中内容...` 作为第一个 `Conversation Ingress Task`。
- `发送到新对话...`，将选区作为上下文卡片打开工作台。
- 拖拽文件或文件夹到对话输入框，转成现有 `@` token。
- `打开 FRIDAY 白板`，自动创建并打开一张 Canvas。
- `添加到白板...`，把选区追加到 FRIDAY Canvas，并记录基础 sidecar 元数据。
- 白板生命周期管理：收集、冻结、发送到新对话、完成后清空或归档、失败后解冻。

暂缓：

- 多文件树选择。
- 文件夹上下文。
- 浮动头像 mini chat。
- 自研白板 UI。
- 一键执行整张白板。
- 多项目批量写入。
- 原文变化后的自动重定位、模糊匹配和路径恢复。

白板相关第一版只做“创建/打开、填入、生命周期管理、选择一批便签发送到新对话”。自动执行修改、异常自动兜底、diff 审批和多项目写入应等基础闭环稳定后再做。

## 12. 后续实现检查点

- 右键菜单是否只在有选区时显示轻量编辑动作。
- 轻量任务是否不创建对话。
- 轻量任务是否只替换当前选区。
- 替换后 `Ctrl+Z` 是否能恢复原文。
- 复杂任务是否新建会话并打开工作台。
- 新会话是否显示来源上下文卡片。
- 多文件上下文是否有数量与预算提示。
- 任务入口是否可从设置中关闭或裁剪。
- `添加到白板...` 是否只收集不执行。
- FRIDAY 是否能一键创建和打开 Canvas 白板。
- 右键添加选区后，Canvas 节点和 sidecar 元数据是否能对应。
- 用户手动拖拽到 Canvas 的内容是否仍保持 Obsidian 原生行为。
- 拖拽文件/文件夹到对话框是否能转成现有 `@` token。
- 项目外来源是否能被标记，并在执行阶段阻止越界写入。
