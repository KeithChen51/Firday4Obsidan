# 官方栏目订阅重构：我们为什么重新定义 F.R.I.D.A.Y 文件夹

> [!note]
> 这篇不是一份功能说明书，也不是 `0.2.9` 的发布日志。它更像一篇幕后笔记，记录我们在这次官方栏目重构里经历过的犹豫、推翻和重新定义。

这轮讨论一开始，其实只是一个很小的问题：每次插件更新时，都把最新的官方文档压到用户 vault 里，这件事是不是有点别扭？

当时我们已经有了 `来自制作组` 这个栏目，也有了 `src/content/studio` 作为官方内容源。构建时，脚本把这些内容编进插件包；插件启动时，再把它们同步到用户的 `F.R.I.D.A.Y/来自制作组` 目录。这个方案能工作，而且很直接。

但越往后想，越觉得它不太对。

问题不在于脚本写得不够好，而在于这个模型把两件本来不同的事情混在了一起：**插件能力更新**和**官方内容更新**。如果只是改一篇指南、补一篇幕后笔记，或者新增一个栏目，用户也必须等插件版本升级。这对内容来说太重了。

更麻烦的是，`F.R.I.D.A.Y/` 这个文件夹本身也已经变得含糊。它曾经放过官方内容，也放过运行时目录、旧项目目录、配置镜像、Agent 兼容目录。站在开发者角度，这些都有历史原因；但站在用户角度，它就是一个看不懂的混合区。

这就是这次重构真正开始的地方。我们不是在改一个文档同步功能，而是在问一个更基础的问题：**`F.R.I.D.A.Y/` 到底应该是什么？**

## 一、先承认旧方案的问题

旧方案的思路很工程化：项目组维护一份内容快照，插件更新后把快照同步到用户本地。为了保证官方内容一致，甚至可以把本地多出来的文件清掉。

这套逻辑在“官方内容是插件附带说明”时说得通。可一旦我们开始认真经营 `Study with F.R.I.D.A.Y`、`从这里开始 · Start Here`、`Changelog` 这些栏目，它就不够用了。

官方内容不只是插件附属品。它是 F.R.I.D.A.Y 和用户持续沟通的地方：解释我们为什么这么做，记录产品设计背后的取舍，也把一些值得复用的使用方法沉淀下来。这样的内容应该能更轻地更新，不应该每次都绑在代码发版上。

还有一个很现实的问题：覆盖。只要我们说“官方目录严格跟随官方快照”，就必须面对用户本地文件可能被覆盖或删除。我们当然可以设计冲突保留、另存副本、本地优先这些策略，但讨论到最后，我们发现这些策略反而会让语义变得更不清楚。

如果这是官方栏目，它就应该以官方为准。如果用户想保留某篇文章的某个版本，或者想在上面写自己的批注，更合适的做法是复制到自己的项目或笔记区，而不是直接在官方栏目里维护一个本地分叉。

这个结论不复杂，但它逼着我们把边界说清楚。

## 二、重新定义 F.R.I.D.A.Y

最后我们把语义收成一句话：

> `F.R.I.D.A.Y/` 是官方频道在用户 vault 里的挂载点。

这句话意味着，`F.R.I.D.A.Y/` 不再是插件运行目录，也不是用户项目目录，更不是系统文件随手落盘的地方。它是官方频道。

它下面的一级目录和一级 Markdown 文件，才是用户可以选择订阅的栏目。

```text
F.R.I.D.A.Y/
  Study with F.R.I.D.A.Y/
  从这里开始 · Start Here/
  Changelog.md
```

这个结构比旧的 `F.R.I.D.A.Y/来自制作组/...` 更干净。`F.R.I.D.A.Y/` 本身就是官方频道，下面的 `Study with F.R.I.D.A.Y`、`从这里开始 · Start Here` 和 `Changelog.md` 是栏目。

这一步看上去只是目录层级变化，实际上是在改产品心智。用户不再需要理解“制作组目录里又有几个子分类”，而是直接看到：这里是 F.R.I.D.A.Y 官方给你的内容，你可以决定订阅哪些栏目。

## 三、为什么是栏目订阅，而不是整包开关

我们也讨论过更简单的方案：给整个 `F.R.I.D.A.Y/` 一个总开关。打开就同步官方内容，关闭就删除整个文件夹。

这个方案实现最轻，但很快会不够用。因为官方内容本身会越来越分化。有人只想看 `Start Here`，不关心研究笔记；有人想追 `Study with F.R.I.D.A.Y`，但不一定需要每次都同步 Changelog。再往后，如果官方频道里出现更多内容，整包开关会变得太粗。

所以第一版就把粒度定在“一级栏目”。一级目录是栏目，一级 `.md` 文件也是栏目。栏目内部不再细分订阅，不做单篇文章开关。这个边界刚好：比整包开关灵活，但不会把设置页做成一个文章管理器。

这里还有一个小但重要的决定：栏目不写死在插件 UI 里。发布脚本扫描 `src/content/studio` 的顶层结构，自动生成栏目清单。以后项目组新增一个一级文件夹，远端 feed 更新后，用户刷新就能看到新的栏目，不需要升级插件，也不需要改设置页代码。

这也是我们第一次真正把官方内容当作“可独立发布的内容产品”来对待。

## 四、从插件内置内容，到远端内容 feed

旧链路是这样的：

```text
src/content/studio
  ↓ 构建时生成
src/content/studio/generated.ts
  ↓ 插件启动时写入
F.R.I.D.A.Y/来自制作组
```

新链路变成：

```text
official/latest.json
official/channels/official.json
official/files/<hash>.md
```

`latest.json` 告诉插件有哪些内容来源。第一版只有 `official`，也就是官方频道。`official.json` 告诉插件官方频道下有哪些栏目，每个栏目有哪些文件。`files/<hash>.md` 保存真正的 Markdown 正文。

这个拆分让插件更新和内容更新终于分开了。

插件版本继续负责能力：`main.js`、`manifest.json`、`styles.css`。官方内容 feed 负责内容：栏目、目录结构、文章正文。两者可以走同一个发布仓库，但不再是同一件事。

这一步对我们来说很关键。因为 `Study with F.R.I.D.A.Y` 这样的栏目，不应该只是 changelog 的附属物。它更像一条持续写作的线索，记录 F.R.I.D.A.Y 怎么学习、怎么调整、怎么犯错又修正。

## 五、严格镜像是一种取舍

订阅之后，栏目采用严格镜像。

官方新增文件，本地创建。官方更新文件，本地覆盖。官方删除文件，本地删除。栏目里多出来的本地文件，也会被清掉。用户取消订阅某个栏目，本地对应栏目会删除。

这听起来不温和。我们一开始也想过要不要做冲突保护：用户改过就不覆盖，或者覆盖前另存副本。后来还是放弃了。

原因是，一旦开始保留本地分叉，官方栏目就不再是官方栏目，而变成了一个同步冲突工作区。同步器需要判断用户为什么改、改动要不要留、官方删除时本地文件算不算用户资产。这些问题没有稳定答案，只会让系统越来越难解释。

所以我们把规则讲直：`F.R.I.D.A.Y/` 是官方频道，不是用户编辑区。想保留、批注、改写，都可以复制出去。订阅官方栏目，就接受官方远端是 source of truth。

这个决定有点硬，但它让用户和系统都不用猜。

## 六、真正让我们谨慎的是历史遗留内容

严格镜像有一个前提：`F.R.I.D.A.Y/` 已经是一个干净的官方频道挂载点。

现实不是这样。历史版本里，`F.R.I.D.A.Y/` 可能还残留：

- `项目/`
- `个人/`
- `Agents/`
- `runtime/`
- `_配置.md`
- 用户自己放进去的其他文件

如果新系统一上来就接管目录，把不属于当前栏目清单的东西删掉，风险很高。尤其是 `runtime/` 这种旧目录，可能因为历史机制没有清理干净。它不应该被新系统误认为“未订阅栏目”，然后直接删掉。

所以我们加了 `legacy safety gate`。

它的逻辑很朴素：任何订阅来源准备覆盖或删除 `F.R.I.D.A.Y/` 前，都先扫一遍根目录。如果发现当前来源没有声明拥有的路径，就只允许刷新 catalog，不允许真正落盘。

也就是说，用户可以看到远端现在有哪些栏目，可以调整订阅，但文件写入和删除会停住。只有当用户迁移、清理，或者明确确认由官方频道接管后，同步才继续。

这不是一个临时补丁。后面如果有社区频道，只要它想写入 `F.R.I.D.A.Y/`，也必须经过同一套 gate。风险控制应该绑定在“谁要接管可见路径”这个动作上，而不是只给官方频道做一次特殊判断。

这也是这轮最重要的反思之一：对用户文件来说，只靠提示文案是不够的。自动检查可能发生在用户还没来得及处理历史内容之前。系统应该先停住，把风险暴露出来，再让用户做决定。

## 七、为什么订阅频道取代斜杠命令

这次我们顺手拿掉了设置页里原本独立展示的“斜杠命令”入口，把位置给了“订阅频道 / Subscriptions”。

这不是因为斜杠命令没用。它仍然可以作为内部能力存在。但它不应该成为 F.R.I.D.A.Y 希望用户首先感知到的东西。

F.R.I.D.A.Y 的方向不是把用户训练成命令操作者，而是尽量把能力放回工作流里。用户应该更多关注项目、笔记、上下文和输出，而不是记住一套显式命令。

官方栏目更适合占这个位置。它是我们解释产品、记录学习、发布指南和反思的地方。第一版只有官方频道，但设置页按“来源 -> 栏目”组织，是为了以后接社区来源时不用推翻重做。

这个选择也提醒了我们：设置页不是功能清单，它在表达产品认为重要的事情。把哪个入口放到前台，本身就是一次产品判断。

## 八、关于默认订阅，我们后来也调整过想法

早期讨论时，我们倾向于“新栏目默认不自动订阅”。理由很合理：远端新增内容，不应该悄悄出现在用户 vault 里。

但落到 `0.2.9` 时，官方频道采用了另一种策略：新发现的官方栏目默认订阅。用户手动关闭后，这个选择会被保留，后续刷新不会偷偷打开。

这个变化不是随手改的。官方频道承担的是第一方说明、入门指南、产品方法和更新记录。它不是任意第三方内容源。对于官方频道来说，默认出现能降低用户错过关键说明的概率。

但这条规则不能直接搬到社区频道。社区来源的信任边界更宽，内容质量和维护节奏也不完全由项目组控制。以后如果开放社区订阅，更稳的策略应该是“发现但不订阅”，由用户主动选择。

所以这里真正的结论不是“所有新栏目都默认订阅”，而是：不同来源需要不同默认策略。官方频道可以主动一点，社区频道必须克制一点。

## 九、这件事带来的学习

这次重构让我最有感触的，不是 `official/latest.json` 或 `OfficialContentService` 本身，而是我们又一次看到了目录语义的重要性。

一个文件夹叫什么、放在哪里、谁有权写入，看起来是很小的工程细节。但在本地优先的产品里，这些细节就是用户信任的一部分。用户看到的文件，天然会被用户理解成自己的资产。插件如果要接管，就必须说清楚接管范围；如果要删除，就必须先确认边界。

`F.R.I.D.A.Y/` 以前太像一个方便的抽屉。我们把官方内容放进去，把运行时状态放进去，把旧系统兼容也放进去。每次都能解释，但解释多了，目录本身就失去了意义。

这次把它收窄成官方频道，是一次必要的减法。减掉运行时痕迹，减掉混合职责，减掉对插件版本的依赖，也减掉同步逻辑里那些看似温柔但难以解释的中间状态。

它还提醒我们，F.R.I.D.A.Y 以后要做的很多事情，都不能只从“功能能不能实现”出发。还要问：这个能力落到用户 vault 里，会不会让边界更清楚？会不会让用户更安心？会不会让未来的自己更容易维护？

## 十、落到代码里的变化

这轮实现最终落在几个地方：

- `scripts/generate-official-content-release.mjs` 负责生成官方内容 feed。
- `official/latest.json` 和 `official/channels/official.json` 描述官方频道和栏目。
- `official/files/*.md` 保存实际 Markdown 正文。
- `src/services/OfficialContentService.ts` 负责刷新 catalog、应用订阅、启动检查和严格镜像。
- `src/services/LegacyFridayRootMigrationService.ts` 负责接管前的 safety gate。
- `src/settings/FridaySettingTab.ts` 的 `subscriptions` 页面取代原来的用户可见斜杠命令入口。
- `src/services/AgentService.ts` 不再负责发布官方内容目录。

但这些文件名不是重点。重点是，官方内容从“插件内置文档”变成了“可订阅、可独立发布、带安全接管边界的官方频道内容”。

这条路还没走完。社区订阅还没开始，栏目内更细粒度的选择也没有做，内容来源的信任模型以后还要重新讨论。但至少这一次，`F.R.I.D.A.Y/` 的意思清楚了。

对一个本地 AI 工作流产品来说，这很重要。因为只有边界清楚，用户才敢让它长期留在自己的知识库里。
