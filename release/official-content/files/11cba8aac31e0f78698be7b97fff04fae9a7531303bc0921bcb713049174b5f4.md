# 四个 Obsidian 内置 Skills 的修订笔记

## 这篇笔记在说什么

这一轮我们重写了 4 个和 Obsidian 直接相关的内置 skill：

- `obsidian-cli`
- `obsidian-markdown`
- `json-canvas`
- `obsidian-bases`

表面上看，这像是在改几份给 AI 用的说明文档；但更准确地说，我们是在修正 4 条会直接影响 agent 行为的“工作规则”。这些规则如果写得过满、过硬，或者和真实环境不一致，最后带来的就不是文案问题，而是误诊、误改和不必要的数据改动。

所以这次修订的目标不是“把说明写得更漂亮”，而是把它们从“语法速查卡”改成“更接近真实工作流的操作准则”。

## 为什么这轮修订值得做

我们在实际使用里发现，内置 skill 最容易出问题的地方，往往不是明显的事实错误，而是下面这几种情况：

- 把一种常见做法写成唯一正确答案
- 没把真实环境中的失败模式说清楚
- 只适合新建 demo，不适合维护已有文件
- 没有提醒 agent 先判断、先保留、先做最小修改

这几类问题单独看都不大，但一旦放进 agent 的执行链路里，就会被放大。一个写得太武断的 skill，很容易把“建议”变成“强制改写”；一个没写清前置条件的 skill，也会让 agent 在错误的环境里盲目执行。

这就是我们这次修订的出发点：不是让 skill 更“会说”，而是让它更“会做”。

## 1. `obsidian-cli`

### 原来的问题

原版 `obsidian-cli` 的方向其实没有偏，它知道自己要解决的是 live vault 操作、插件调试、CLI 交互这些事情。但它默认了一个过于理想的前提：只要输入 `obsidian ...`，命令就应该能工作。

这个前提在真实环境里并不稳，尤其是 Windows：

- 当前 shell 里不一定已经拿到正确的 `PATH`
- 安装器版本可能过旧
- `Obsidian.com` 可能缺失
- CLI 开关可能开了，但终端命令仍然不可用

换句话说，原版 skill 更像一张命令卡片，但在真正开始操作之前，少了最关键的一步：先确认这台机器上的 CLI 到底是不是可用。

### 这次怎么改

这次我们把 `obsidian-cli` 改成了“先诊断，再操作”的结构。

最重要的变化有三点：

- 增加本地预检，先跑 `where obsidian`、`obsidian version`、`obsidian eval`
- 把 Windows 下最常见的故障模式写明白，包括 `Obsidian.com`、安装器版本和 `PATH`
- 明确 `obsidian help` 是本地帮助入口，外部网页文档只是补充

### 改完之后的变化

它现在不再假设环境天然正确，而是先帮助 agent 判断环境，再决定下一步。这让它从“命令列表”变成了一个更可靠的本地入口。

## 2. `obsidian-markdown`

### 原来的问题

原版 `obsidian-markdown` 没有太多硬伤，但它有一个很典型的问题：把 Obsidian 社区里常见的语法偏好，写成了过于绝对的规则。

最明显的一条就是内部链接。原版几乎把 `[[wikilinks]]` 写成了唯一正确的内部链接方式，而把 Markdown-style links 降格成“主要给外部链接用”。

这会带来两个实际后果：

- agent 容易把本来就合法的内部 Markdown links 统一重写成 wikilinks
- 在编辑已有笔记时，会把“保持原有风格”让位给“统一格式”

### 这次怎么改

这次我们给它补上了两类非常重要的边界：

- 说明 Markdown-style internal links 在 Obsidian 里同样是合法内部链接
- 增加“编辑已有笔记时优先保留原有风格”的护栏

同时我们还收窄了 alias，避免它因为 `markdown` 这类过宽触发词而误伤普通 Markdown 任务。

### 改完之后的变化

它现在的重点不再是“把所有笔记改成同一种语法”，而是“在 Obsidian 语境下安全地创建和编辑内容”。这更符合实际写作，也更尊重已有笔记。

## 3. `json-canvas`

### 原来的问题

这 4 个 skill 里，`json-canvas` 是问题最严重的一个，因为它已经碰到了规范层面的错误。

原版里有一条规则写成了“节点 ID 应该是 16 位小写十六进制字符串”。这听起来很像一条规范，但它其实不是 JSON Canvas 的硬要求。真正的要求只是：ID 需要是唯一字符串。

这类错误的危险不在于一句话本身，而在于它会驱动 agent 去做错误的“修正”：

- 把合法文件判断成不合法
- 重写本来应该保留的既有 ID
- 在维护已有 canvas 时引入不必要的数据变动

### 这次怎么改

这次我们做了两层处理：

- 把“规范要求”和“布局建议”分开写
- 明确告诉 agent：维护已有 canvas 时，要尽量保留 existing IDs、unknown fields 和 node order

同时补上了更多真实编辑会遇到的字段信息，比如 edge 的常见字段、`subpath` 这类容易被忽略的部分。

### 改完之后的变化

它终于从“能生成一个简单白板的说明卡”，走到了“可以比较安全地维护已有 `.canvas` 文件”的水平。这一步很重要，因为绝大多数真实工作不是从零开始画，而是在已有文件上继续改。

## 4. `obsidian-bases`

### 原来的问题

`obsidian-bases` 的问题不是写错，而是写得太浅。它能让 agent 大概知道 `.base` 文件长什么样，但不足以指导真实维护。

原版最大的问题是它没有把“结构”和“流程”分开：

- 讲了 YAML 大概长什么样
- 但没讲改动时应该先判断什么
- 也没讲 standalone `.base` 和嵌入式 `base` block 的差异

结果就是，agent 虽然知道它长什么样，却不一定知道该怎么安全地下手。

### 这次怎么改

这次我们给它补上的，主要是工作流层的内容：

- 先区分独立 `.base` 文件还是嵌入式 `base` block
- 修改前先 parse YAML，再确认顶层结构
- 先校验公式、属性、视图引用，再决定改哪里
- 优先做最小修改，尽量保留无关 section 和原有顺序

### 改完之后的变化

它不再只是“一个结构样例”，而更像一份可以指导真实维护的说明。对于已经有内容的 Bases 文件，这种差别其实非常大。

## 这四次修改背后的共同原则

如果把这次修订抽出来看，会发现 4 个 skill 最终都在朝同一个方向收敛：

- 先判断环境，再执行操作
- 先尊重现有内容，再考虑统一格式
- 先区分规范和偏好，再写规则
- 先做最小修改，再考虑重写

这听起来不像某一条具体语法规则，但它恰恰是 agent 真正需要的东西。因为 agent 面对的不是“空白文件”，而是用户已经在用的 vault、已经存在的 `.canvas`、已经写好的 Markdown、已经成型的 Bases 配置。

说到底，我们不是在教它“如何写一个例子”，而是在教它“如何在真实内容上不犯错”。

## 这件事如何体现在产品里

为了不让这次修订只停留在源码和 changelog 里，我们还把相关背景直接放进了技能页：

- 对已经修订过的 Obsidian skill，在名称旁显示一个注释图标
- 悬浮或点击后，可以看到“原来是什么、为什么不够好、改成了什么”

这样做的目的很简单：让后续查看这些 skill 的人，不需要翻代码，也能理解这轮调整到底解决了什么问题。

## 这篇笔记想留下的结论

这轮修订最重要的收获，不是把 4 个 skill 写得更完整，而是把一件事情想清楚了：

对于和文件直接打交道的 agent 来说，一个好的 skill 不只是“知道怎么做”，还要“知道什么时候先别急着做”。

如果以后还要继续修这类 Obsidian skill，这个判断标准应该继续保留：

- 它是不是尊重真实环境
- 它是不是尊重已有内容
- 它是不是区分了规范、建议和个人偏好
- 它是不是在帮助 agent 少犯错

只要这几条还成立，skill 的内容就会越来越像可靠的工作规则，而不是漂亮但脆弱的说明文字。
