# 幕后笔记元数据规范

## 一、为什么要专门给幕后笔记定一套元数据

幕后笔记和开发灵感、实现计划、普通知识笔记不一样。

它们最重要的价值，不是记录某个零散事实，而是沉淀：

- 我们为什么做出某个产品判断
- 这篇笔记属于研究、决策、复盘，还是架构说明
- 它现在是草稿、稳定结论，还是历史归档
- 它和哪些源文档、相关笔记有关

如果这类笔记的 frontmatter 每篇都随手写，短期看问题不大，长期会出现三个麻烦：

1. 人很难快速筛出同类笔记。
2. AI 很难稳定判断“这篇笔记是什么性质”。
3. 后面即使内容都在，检索和串联上下文也会越来越不稳。

所以幕后笔记需要一套比普通笔记更稳定的元数据约定。

## 二、设计原则

这套元数据规范遵循四条原则：

### 1. 轻量

字段不能太多。
如果 frontmatter 比正文还难维护，这套规范就会失效。

### 2. 稳定

同一类信息只保留一个字段，不做多套重复分类。

### 3. 对人和 AI 都友好

这套属性既要让人一眼理解，也要让 AI 更容易检索、归类、串联。

### 4. 服务产品思考，而不只是归档

幕后笔记不是简单存档，所以元数据要优先表达：

- 性质
- 状态
- 摘要
- 来源

而不是只表达“作者是谁、日期是什么”。

## 三、统一后的字段方案

### 必填字段

```yaml
---
title:
series: behind-the-build
type:
status:
author:
created:
updated:
summary:
release_scope: []
tags: []
---
```

### 选填字段

```yaml
aliases: []
topics: []
related_notes: []
audience:
```

## 四、每个字段的含义

### `title`

必须有。
不要完全依赖文件名替代标题。

### `series`

固定写：

```yaml
series: behind-the-build
```

它的作用是明确说明：这篇笔记属于“幕后笔记”系列，而不是开发灵感、计划、普通知识卡片。

### `type`

建议只用少量枚举，不自由发挥。

推荐值：

- `research`
- `decision`
- `architecture`
- `retrospective`
- `ship-note`

### `status`

也建议固定枚举：

- `draft`
- `stable`
- `archived`

### `author`

这个字段保留。

原因不是为了形式感，而是后面这类笔记可能不止一个人写，所以应该假定未来存在多人协作。

### `created` / `updated`

格式统一为：

```yaml
created: 2026-04-20
updated: 2026-04-20
```

幕后笔记按日期粒度记录就足够。

### `summary`

这个字段非常重要，建议每篇都写。
它最好是一句话，说明：

- 这篇笔记在讲什么
- 为什么值得读

### `release_scope`

这个字段用来标记这篇幕后笔记主要对应哪个版本阶段。

推荐统一写成列表，即使只有一个版本也这样写：

```yaml
release_scope:
  - 0.2.6
  - 0.2.7
```

如果一篇笔记跨越多个版本，可以写成：

```yaml
release_scope:
  - 0.2.6
  - 0.2.7
```

如果这篇笔记本身是规范或元规则，不对应某个具体版本，可以写：

```yaml
release_scope:
  - meta
```

我建议使用 `release_scope`，而不是 `version`。

因为幕后笔记常常不是“一个版本里的一个功能说明”，而是“覆盖一个版本阶段、甚至跨多个版本逐步成形的产品思考”。  
`release_scope` 比单点版本号更贴近真实情况。

### `tags`

保留，但保持克制。

推荐至少包含：

- `friday`
- `backstage`

然后再加 2 到 4 个主题标签即可。

### `aliases`

用于常见简称、中英混合别名和更稳定的检索命中。

### `topics`

如果 `tags` 偏向搜索标签，那么 `topics` 更适合表达这篇笔记主要覆盖的主题块。

### `related_notes`

这个字段适合放延伸阅读、并行主题，或者读完当前笔记后值得继续看的相关内容。

### `audience`

这是一个可选字段。
如果没有明确必要，可以不写。

## 五、我不建议保留的字段

### 不建议同时出现多套分类字段

例如：

- `category`
- `theme`
- `domain`
- `subject`

这些字段很容易和 `type / topics / tags` 重叠。

### 不建议为了“完整”而加入大量空字段

如果某篇笔记没有：

- `aliases`
- `topics`
- `related_notes`

那就直接不写，不要强行留空数组。

## 六、推荐模板

```yaml
---
title: Friday的Memory、Agent与Soul统一定义
series: behind-the-build
type: architecture
status: stable
author: Keith Lim
created: 2026-04-20
updated: 2026-04-20
summary: 统一说明 Friday 为什么重做 memory、让 Agent 退场、引入 Soul，并采用本地状态层与 Vault 双根架构。
release_scope:
  - 0.2.6
  - 0.2.7
tags:
  - friday
  - backstage
  - memory
  - soul
  - ai-native
aliases:
  - Friday统一定义
topics:
  - memory
  - soul
  - local-state
  - vault-boundary
---
```

## 七、为什么这套 schema 从产品视角是对的

因为幕后笔记本质上不是知识库碎片，而是“产品判断的沉淀层”。
它最该表达的，不是作者情绪，也不是随手贴标签，而是：

- 这是什么性质的判断
- 现在成熟到什么程度
- 它和哪些决策有关

所以：

- `type`
- `status`
- `summary`
- `related_notes`

比单纯堆 tags 更有价值。

## 八、为什么这套 schema 从 AI Native 视角也是对的

AI 在读取一批笔记时，最怕的是：

- 每篇结构都不一样
- 同类文档没有统一标识
- 研究、决策、复盘看起来像同一种东西

统一 frontmatter 后，AI 更容易做到：

- 判断这是不是正式决策
- 判断这篇笔记是不是当前有效结论
- 知道它和哪些相关文档有关
- 在长上下文里更稳定地引用它

所以这套元数据规范不是“为了笔记软件而规范”，而是在给未来的人和 AI 同时提供更稳定的理解入口。

## 九、当前幕后笔记目录的执行建议

当前 `Behind the Build` 目录建议立即遵守这套规范。

执行顺序建议是：

1. 先把已有笔记 frontmatter 统一。
2. 再逐步修正文中存在乱码或历史遗留的问题。
3. 以后新写幕后笔记时，直接套用这份模板。

## 十、一句话总结

幕后笔记的元数据不应该只是“文件属性”，而应该是 Friday 幕后知识体系的索引层。
这层如果不统一，后面的产品复盘、设计传承和 AI 检索都会越来越乱。
