# FRIDAY 的 Memory、Agent 与 Soul 统一定义

> [!note]
> 这份文档不是某一轮实现的变更日志，也不是给工程师看的纯技术说明。它的目标是把我们关于 Hermes、tools、memory、Agent、Soul、Vault、本地状态层、迁移与清理策略的讨论，整理成一份能让非专业人士也读懂的幕后说明——同时也是一份以后出现分歧时可以回来查阅的决策文档。

---

## 一、先说结论

如果把这一整轮讨论压缩成一句话：

> FRIDAY 正在从"一个把内部状态写进 Vault 的 Obsidian 插件"，演进为"一个拥有独立状态层、以 Obsidian 为重要入口的本地 AI 工作流产品"。

在这条主线上，`memory`、`Agent` 和 `Soul` 分别承担了三种完全不同的角色：

**Memory** 是 FRIDAY 的 durable facts 层。它只负责保存长期、稳定、值得被记住的事实，不包含全部的长期状态或过程性信息。

**Soul** 是 FRIDAY 的角色概念层。它用来表达 FRIDAY 的人格、风格和工作姿态，而不是一个独立的运行时容器或系统实例。

**Agent** 是一个正在退场的历史兼容概念。它主要作为迁移边界存在，不再作为长期用户概念或运行时的真实来源。

也就是说，这轮不是在修几个文件名，也不是在堆几个功能，而是在重写 FRIDAY 的"自我认知"。

以后只要再讨论"这个东西算不算 memory""这个状态要不要挂到 Soul 下面""这个文件夹要不要放在 Vault 里"，优先先问这四个问题：

1. 这是角色定义，还是系统状态？
2. 这是 durable fact，还是过程性信息？
3. 这是用户资产，还是 FRIDAY 内部资产？
4. 这个状态应该跟随用户（全局），还是跟随项目？

---

## 二、这轮思考为什么会开始

这轮重构的起点，不是 FRIDAY 自己出了什么问题，而是我们去深入研究了 Hermes。

Hermes 是一个成熟的 AI Agent 框架，我们重点研究了它的 agent loop、tools runtime、skills、memory、prompt assembly、session storage 和 context compression。研究完之后，得到的第一层认识并不是"我们要做一个 Hermes"，而是：

> Hermes 的成熟度，并不主要来自工具多，而是来自分层清楚。

Hermes 把工具、技能、持久记忆、历史召回和提示词组装分得很清楚，每一层的职责都有明确的边界。FRIDAY 当时的问题，恰好就出在这些边界上还不够稳——很多概念混在一起，系统行为难以解释，也难以维护。

所以 Hermes 对 FRIDAY 真正的价值，不是提供了一堆要照抄的功能，而是像一面镜子，让我们看清 FRIDAY 自己最缺的到底是什么。

看清这一点之后，我们面临一个选择：是跟着 Hermes 的功能清单逐项补齐，还是先把自己最重要的两件事做稳？

如果只盯着功能数量，FRIDAY 很快会变成一个看起来很强、实际上越来越乱的功能堆。真正决定一个 AI 产品能不能长期工作的，不是它有多少工具，而是它的"思维"是否清晰——它如何理解上下文、如何管理长期状态、如何与用户建立稳定的协作关系。

因此，我们把这轮的重心收敛到两个维度：**工具层**和**记忆层**。

### 工具层：少而精，深而专

工具层决定了 FRIDAY 能不能真正行动。但这里重要的不是工具越多越好，而是工具的边界是否清楚、是否在为 FRIDAY 的核心场景服务。

FRIDAY 的核心场景是 Obsidian、本地文件、项目知识、研究与写作和持续协作。它不是浏览器自动化工具，不是消息平台，也不是家庭设备控制中心。所以 FRIDAY 的工具层应该少而精，深刻理解 Vault 的结构、项目边界和知识工作流，而不是长成"所有 agent 都会有的通用功能集合"。

### 记忆层：长期状态的秩序

如果说工具决定了行动，那么记忆决定了 FRIDAY 做事时会不会越来越聪明，还是越来越混乱。

FRIDAY 当时最明显的问题，不是"记不住东西"，而是"记忆结构分裂"。类似 memory、knowledge、session history 和 role profile 的内容混杂在一起，系统没有一个清楚的统一解释。写入和读取不是同一套语义，用户也很难知道 FRIDAY 到底在记住什么。

这让我们意识到：FRIDAY 当前最该补的，不是更多能力，而是长期状态的秩序。这正是 `memory v1` 成为整轮设计主轴的原因。

## 三、核心决策

### 3.1 为什么让 Subagent 先退场

在进入 memory 细化之前，我们非常早就做了一个关键决定：把 `subagent` 从 FRIDAY 当前路线里完全移除。

这个决定之所以重要，是因为它直接定义了 FRIDAY 现在"不想成为什么"。多代理架构会天然引入一整套额外复杂度：多代理上下文隔离、任务拆分和结果汇总、权限传递、trace 合并、记忆归并，以及随之而来的 UI 解释成本。而在当时，FRIDAY 连单代理的长期状态都还没收口。如果这时继续做多代理，就像地基还没稳，先去加楼层。

这个决定逼着我们把 FRIDAY 的现阶段定位讲清楚：单代理、强上下文、强文件边界、强知识工作流，暂时不承担多代理编排复杂度。只有先收紧这条边界，后面的 memory、Soul 和本地状态层才不会被拖偏。

### 3.2 Memory v1：从零开始，记得对

真正深入看 FRIDAY 的旧 memory 之后，我们很快意识到问题不只是"某条规则有 bug"，而是 FRIDAY 根本没有一个统一的记忆模型。当时并存着 agent 级的 `facts.md / preferences.md`、`_global/knowledge/` 里的用户画像和偏好、runtime 真正读取的另一套路径，以及自动抽取和追加式写入逻辑。同样叫"记忆"的东西，系统内部有多种来源，写入和读取不是同一套语义。

因此我们没有选择继续打补丁，而是直接废弃旧 memory 模式，建立 `memory v1`。

`memory v1` 的核心目标不是"记得更多"，而是建立一个边界清晰、可解释、可修正的 durable facts 层。这意味着 memory 是一个高度克制的系统：只有稳定、会复用、不只对当前一轮有用的信息，才值得进入 memory。而当前任务进度、会话中的临时计划、一次性推理过程、session 摘要、方法论和可复用操作步骤，再重要也不应该进 memory——这些东西要么属于历史，要么属于程序化知识。

这条边界被我们收成了一句话：**`memory = durable facts`，`skill = procedural knowledge`**。

在具体实现上，`memory v1` 的每一个设计决定都有明确的理由：

**只做两层（global + project），暂不涉及 session recall。** 如果第一版就把 durable memory 和 transcript recall 混在一起，系统复杂度会立刻膨胀。先只做 durable facts，不做全部长期状态。

**`project memory` 必须绑定当前项目。** 没有激活项目时不能写 project memory，切换项目时 project memory 跟着切换。这直接解决了跨项目污染问题，让 FRIDAY 终于不再把"项目事实"和"用户全局偏好"混成一团。

**显式工具写入优先，不做自动抽取。** 自动抽取太容易产生脏数据，而 FRIDAY 当前最需要的是可控。只有显式写入，replace/remove 和 trace 才有意义。旧的自动 memory 抽取链路应该整体下掉，而不是继续留着做"兜底"。

**每轮默认注入 global + 当前项目 memory。** 不是按需召回，不是模糊命中，而是固定注入。因为 FRIDAY 当前对话天然绑定项目，这种方式反而最稳——让模型每轮都能稳定拿到用户长期偏好和当前项目长期约束，而不是时有时无。

**第一版就支持 `replace/remove`。** 如果 memory 只有 `add`，记忆会越写越脏，偏好变了也改不了，项目规则更新了只能继续往后堆。三种动作做全，memory 才是一个能长期维护的系统，而不是只会膨胀的文本堆。

**写入默认不需要人工确认，但必须可见、可修正、可追溯。** 我们已经通过显式工具优先、不做自动抽取、replace/remove 可修正、trace 可追踪等方式控制了风险。如果还要求每次写入都人工确认，体验会迅速变重。

**存储格式采用单文件 Markdown，逐条列表。** 不是为了"最先进"，而是为了第一版最稳：好读、好注入 prompt、好 replace/remove、好调试。

**写入后下一轮生效，当前轮不回写 prompt。** 这体现的是 prompt 快照思维。如果本轮立刻生效，会导致同一轮上下文漂移，系统行为更难解释。

### 3.3 数据 Ownership 与双根架构

当 memory 和本地状态层逐渐变清楚之后，一个老问题开始变得越来越刺眼：`FRIDAY/Agents` 目录到底是什么？

从用户角度看，这个目录很容易产生误解——`Agents` 像是"我在管理多个助手"，`memory` 像是"AI 真正在用的记忆"，`sessions` 像是"我需要理解和维护的内容"。但从系统角度看，它实际上混着旧角色资料、旧 memory 痕迹、sessions、snapshots、approval store、presets 和 global knowledge。目录名和真实职责已经错位。

一开始我们讨论的是"要不要把 `_runtime` 隐藏"，但很快意识到这只是在改显示方式，并没有解决数据归属的问题。真正该先回答的是：什么属于用户知识空间，什么属于 FRIDAY 自己的运行时状态，哪些状态应该跟人走，哪些状态应该跟项目走。

这一步，直接引出了双根架构：

**Vault Root** 只保留用户能理解、愿意拥有、可能会编辑的资产——项目文件、知识笔记、输出结果。

**FRIDAY Local Data Root** 只保留 FRIDAY 自己的系统状态：souls、sessions、approvals、snapshots、traces、cache、global memory。

基于这个原则，`global memory` 存放在本地状态层，因为全局偏好属于"人"，不属于某个 Vault——如果用户切换 Vault 后全局偏好也跟着没了，那就不是真正的 global memory。而 `project memory` 存放在项目隐藏目录，因为项目记忆本来就应该跟项目一起移动——用户复制、归档或移动项目时，项目记忆也应该自然跟着走，而不是被困在 FRIDAY 的本地数据库里。

这一步不只是目录调整，而是产品定位的变化：FRIDAY 不再是"把内部状态写进 Vault 的插件"，而是"有自己状态层的产品，Obsidian 只是一个前端入口"。这也意味着，如果将来 FRIDAY 不满足于 Obsidian 插件，本地状态层可以直接复用，不需要重新迁移。

### 3.4 从 Agent 到 Soul：人格层的重塑

在数据分层更清楚之后，我们回过头重新审视用户层概念。

`Agent` 这个词的问题在于，它太像一个独立的系统实例——"多个 Agent"让人联想到多个并行助手或多个系统实例。但 FRIDAY 真正想表达的不是这些，而是同一个 FRIDAY 在不同场景下的不同人格层、不同角色模式、不同语气和行为约束。

`Soul` 这个命名一旦确定，很多事情都突然顺了。`Soul` 是 FRIDAY 的角色变体层，负责表达角色定位、语气风格、行为约束、避免事项、关联 preset 和可选模型偏好。它不是 memory 容器，不是 session 容器，也不是独立 runtime 实例。这条定义非常重要——如果不提前说清楚，新的 `Soul` 很快就会再次长成旧 `Agent` 那种"什么都往里挂"的超级容器。

这个命名的转变，不仅在概念上更准确，更重要的是它帮助我们把用户层概念和底层存储结构彻底分开：用户看到的是 `Soul`，系统存的是结构化 Soul 定义，底层不再需要继续围绕 `FRIDAY/Agents` 组织全部状态。

对于现有的 `Agent` 数据，升级路径遵循三个原则：自动迁移优先，保证用户可以继续使用；旧 `FRIDAY/Agents` 不在第一次升级时直接删除；设置页提供显式清理按钮，由用户自己决定什么时候做收尾，并且文案必须说清楚会删除哪些可见资产。这不是纯工程判断，而是一个产品判断：当用户量还不大、历史债务很重时，可以接受强清理，但不能假装它只是"安全整理"。

## 四、这轮调整真正在做什么

如果只从传统软件架构的角度看，这轮事情像是在做目录重构、概念重命名、路径迁移和自动迁移。但从 AI Native 的视角看，我们实际上是在为 FRIDAY 建立三种核心秩序：

**角色秩序**：通过 `Soul`，让 FRIDAY 的人格层清楚起来。用户知道自己在和哪个"FRIDAY"说话，系统也知道当前应该以什么姿态工作。

**长期状态秩序**：通过 `memory v1`，让 FRIDAY 的 durable facts 清楚起来。什么该记，什么不该记，写入和读取遵循同一套语义，用户可以理解和修正。

**状态 Ownership 秩序**：通过双根架构，让"用户知识"和"系统状态"分开。用户资产归用户知识空间，FRIDAY 运行时状态归 FRIDAY 本地状态层，项目级 durable facts 跟项目走，全局 durable facts 跟人走。

一个 AI Native 产品最怕的不是功能少，而是这些东西混在一起：角色是谁不清楚，长期记忆记什么不清楚，哪些是项目边界哪些是系统边界不清楚，用户该看到什么系统又在背后存什么也不清楚。这些东西一旦混乱，用户很快就会感觉 AI 时灵时不灵、说话风格不稳定、记得一些奇怪的东西却忘掉真正重要的东西。

这三种秩序一旦建立，FRIDAY 才有资格成为一个真正长期可协作的 AI 产品，而不是一个短期可用的插件面板。

## 五、核心概念速查

以下是这一整轮讨论中最重要的定义，供以后直接查阅。如果未来这些定义与其他文档出现冲突，应优先修订本文，让它继续承担"统一口径"的角色，而不是让新的决策再次散落。

| 概念 | 定义 |
|------|------|
| **FRIDAY** | 一个拥有独立状态层的本地 AI 工作流产品。Obsidian 是当前最重要的入口之一，但不是 FRIDAY 的全部宿主。 |
| **Vault** | 用户的知识空间，不是 FRIDAY 内部系统状态的总容器。 |
| **Soul** | FRIDAY 的角色概念层。表达人格、语气、行为约束和角色定位，不表达独立运行时实例，不是状态总容器。 |
| **Memory** | FRIDAY 的 durable facts 层。只保存稳定、可复用的长期事实，不保存全部长期状态。 |
| **Global Memory** | 用户级长期偏好，跟随用户，不跟随 Vault。存放在 FRIDAY Local Data Root。 |
| **Project Memory** | 项目级长期约束，跟随项目，必须绑定当前激活项目 root。存放在项目隐藏目录。 |
| **Skill** | 负责 procedural knowledge（程序化知识）。方法论、步骤法和固定工作流应进入 skill，而不是 memory。 |
| **Agent** | 历史兼容概念。仅存在于迁移和清理边界，不再作为长期用户概念或运行时真源。 |
| **FRIDAY Local Data Root** | FRIDAY 的本地状态层，存放 souls、sessions、approvals、snapshots、traces、cache 和 global memory。 |
